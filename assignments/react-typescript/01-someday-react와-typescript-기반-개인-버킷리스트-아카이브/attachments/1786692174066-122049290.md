# Someday 프로젝트 작업 규칙

## 역할과 기준

- `PROJECT_PLAN.md`를 프로젝트 범위, 기술 선택, 데이터 구조, 개발 순서의 최우선 기준으로 사용한다.
- 작업을 제안하거나 시작하기 전에 현재 파일과 구현 상태를 확인하고, 계획서 기준으로 완료 단계와 다음 단계를 판단한다.
- 계획서보다 나은 구현 방법이 있으면 설명할 수 있지만, 사용자 승인 없이 프로젝트 범위나 개발 순서를 변경하지 않는다.
- Claude Code가 메인 구현을 담당한다. Codex는 기본적으로 현재 상태 검토, 다음 단계 안내, 코드 리뷰, 테스트와 검증, 구현 방향 설명을 담당한다.

## 변경 권한

- 사용자가 명시적으로 코드 수정을 요청하기 전에는 소스 코드, 설정 파일, 문서 파일을 수정하지 않는다.
- 사용자가 현재 단계의 구현을 요청하더라도 다음 개발 단계를 자동으로 이어서 진행하지 않는다.
- 요청받은 단계에 필요한 기능만 구현하고, 이후 단계의 기능을 앞당겨 추가하지 않는다.
- 기존에 정상 동작하는 구조와 디자인은 현재 작업에 필요하지 않으면 변경하지 않는다.

## 기술 및 범위

- React + Vite + TypeScript + Tailwind CSS 기반 구조를 유지한다.
- 프로젝트 계획에 명시된 Lucide React, date-fns, localStorage 사용 방향을 따른다.
- 필요성이 확인되지 않은 라이브러리, 상태관리 도구, 프레임워크를 추가하지 않는다.
- 백엔드, 데이터베이스, 인증, 외부 데이터 서비스는 계획서의 향후 확장 범위이며 사용자의 명시적 요청 없이 추가하지 않는다.
- 역할이 명확한 파일만 분리하고, 초기부터 과도한 추상화나 폴더 구조를 만들지 않는다.

## 구현 및 검증

- 코드 수정 요청을 받으면 변경 전 관련 코드와 현재 작업 트리 상태를 확인한다.
- 구현 후 최소한 `npm run build`를 실행해 TypeScript 타입 검사와 Vite 빌드를 확인한다.
- 관련 테스트 명령이 존재하면 실행하고, UI 작업은 가능하면 개발 서버와 실제 브라우저에서 PC·모바일 동작을 검증한다.
- 오류나 경고가 발생하면 원인을 확인하고 요청 범위 안에서 수정한다. 검증하지 못한 항목은 성공한 것처럼 보고하지 않는다.
- 사용자 소유의 기존 변경사항과 관계없는 파일은 수정하거나 되돌리지 않는다.

## 작업 보고

- 안내 요청에는 완료 단계, 다음 단계, 구현 범위, 작업 이유, 구현 요청 예시, 테스트 항목, 다음 단계 전 확인사항을 초보자도 이해하기 쉽게 설명한다.
- 코드 작업 후에는 수정한 파일, 구현한 기능, 실행한 테스트와 결과, 아직 구현하지 않은 기능, 다음 계획 단계를 간단히 요약한다.
